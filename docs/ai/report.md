# GachaChess: проверяемая модель сложности

## 1. Как работал AI

Рейтинг → округление до 50 → Skill Level 0–12 и 1500–20000 узлов → Stockfish 19 smallnet WASM Worker → bestmove. UCI_LimitStrength=false, MultiPV по умолчанию 1. CP/mate/info игнорировались. Это внутренние уровни, не калиброванные человеческие рейтинги: даже минимальный Skill выбирает сильные шахматные продолжения. Нет прямого контроля над ошибками. Полный аудит и план сохранены отдельным коммитом до реализации: `integration-plan.md`.

## 2. Integration design

Player Elo → target → сохранённые effective Elo + seed → один Stockfish MultiPV search → нормализация/легальность/контекст → pure probability model → seeded выбор → существующий applyMove.

Переиспользованы Worker, адаптер, chess.js, PGN, taskId, сохранения. API `{id,fen,pgn,engineProfile} → {id,move}` сохранён. Debug analysis возвращается только по запросу simulation harness, ничего не записывает в пользовательскую telemetry. Старые stockfish18/19-v1 и JS-партии продолжают работу с прежней моделью. Новый профиль `humanized19-v1` фиксирует seed и силу; новые версии формул должны получать новый profile id.

Native UCI strength НЕ включён и переходного диапазона в поставленной версии НЕТ. Установленный движок объявляет UCI_Elo 1320–3190, но это не человеческий Elo приложения. Непроверенная смесь режимов нарушила бы требование воспроизводимости и могла бы создать скачок. В конфигурации нет неработающих переключателей. Возможный native-переход требует отдельной проверки и допускается архитектурой адаптера, но не реализован как неподтверждённая функция.

## 4. Итоговая математическая модель

Обозначения: E — effective Elo бота, s — skill, L — нормализованная потеря.

```
target = clamp(playerElo - 100, 400, 1600)
variance = clamp(N(0,40²), -120, 120)  // один раз на партию
E = clamp(target + variance, 400, 1600)
s = clamp((E - 400) / 1200, 0, 1)
```

Variance получена Box–Muller из seeded Mulberry32. Seed партии генерируется один раз; seed хода = FNV-подобный hash(seed партии, FEN). Clipping у границ снижает фактическую σ и смещает среднее внутрь диапазона. Отображается target, скрытая variation не меняет уровень каждый ход.

Базовые ошибки:

```
inaccuracy = .35 × (1-s)^1.2
mistake    = .28 × (1-s)^2.3
blunder    = .16 × (1-s)^3
best       = min(остаток, .10 + .45 × s^1.3)
good       = остаток - best
```

Каждая ошибка умножается на complexity × phase × winning. Если суммарная масса ошибок > .95, она пропорционально уменьшается до .95; best/good делят остаток. Вероятности неотрицательны и суммируются в 1. Степени ошибок отличаются от начальной гипотезы для более быстрого снижения серьёзных ошибок; отдельных Elo-таблиц нет.

Complexity = clamp(1 + .10 при >=30 legal moves + .10 при >=3 вариантах с L<.15 + .20 при >=5 взятиях/шахах − .25 при <=2 legal moves, .75, 1.5).

Phase: opening до 16 полуходов ×.75; endgame при сумме материала обеих сторон <=16 ×1.15; иначе middlegame ×1.0. Endgame проверяется первым. Стоимости: пешка1, конь/слон3, ладья5, ферзь9, король0.

При best evaluation >3: winning = 1 + .25 × (1 − clamp((E−600)/600,0,1)); иначе 1. Это плавная замена ступенчатым коэффициентам преимущества. Проигрывающий бот не получает усиления.

UCI CP /100 — оценка с перспективы root side-to-move. Для хода чёрного бота знак **не инвертируется**: root уже чёрный. В общем нормализаторе знак меняется только если botSide != rootSide. Mate преобразуется отдельно: sign(mate) × (100 − .1×min(|N|,50)); CP ограничен ±50. Mate=0 трактуется как проигранный мат. Это шкала utility, не утверждение, что мат стоит 100 пешек. L=maxEvaluation−evaluation. Границы категорий: best<.15, good<.40, inaccuracy<.90, mistake<1.80, blunder>=1.80.

Мат в 1: 1−.35×(1−s)^3.4. Мат в 2: 1−.8×(1−s)^1.65. Сначала выбирается, распознан ли мат; затем выбор внутри соответствующего пула. Если альтернатив нет, выбирается мат. При пропуске мата выбирается оценённое продолжение; намеренный отказ от мата — явное исключение из обычного fallback только вверх. Mate-in-2 опирается на доказанную движком PV, не на человеческое зрительное распознавание.

Внутри выбранной категории вес = exp(−(L−minL)×(.5+2.5s)) × guardWeight. Вычитание minL сохраняет распределение и предотвращает underflow. Пустая категория заменяется ближайшей более сильной. Никакого random legal fallback.

Guard: тихий ход ферзём/ладьёй с L>=1.8, после которого фигуру можно сразу взять, получает вес .15. Дополнительно с вероятностью .85 заменяется более безопасным оценённым ходом. Шахи и взятия не запрещаются как потенциальные жертвы. Это мягкая эвристика, не SEE. Все кандидаты проходят chess.js legality, поэтому шах/рокировка/превращения не обходят правила. При единственном legal move выбор однозначен.

Поиск: Threads=1, Hash=16MB, Skill=20, UCI_LimitStrength=false, MultiPV=min(32,legalCount), depth<=10, nodes<=500000. Один search на ход. Movetime в production отключён ради повторяемости; watchdog 15 секунд завершает зависший worker ошибкой, не случайным ходом. Инициализация ограничена 60 секундами. Берётся последняя **полная уникальная пачка одной глубины**; bounds и незавершённые/смешанные пачки не используются.

Почему 32: исходные 12 PV давали в спокойном миттельшпиле только L<=.28, а в дебюте только L<=.41. Запрошенная ошибка отсутствовала, и fallback усиливал бота. При 32 PV появились умеренные потери без неоценённых ходов. Цена — больше engine work; глубина на наборе получилась 9–10.

## 5. Методика симуляции

14 фиксированных позиций. На позицию один production-анализ; затем 1000 решений ×7 Elo = 98000 выборов, по 14000 на каждый Elo. Seed основной серии 20260912, отдельные регрессионные серии 7 и 91 (ещё по 98000 решений). В таблице указан **effective Elo бота**, не player Elo; variance не подмешивается в измерение собственной функции силы.

Контрольный анализ не участвует в выборе: MultiPV для всех legal root moves, depth<=14, nodes<=1600000, time<=8000ms. Получена глубина 11–14. Таким способом можно оценить любой выбранный новый или старый ход одним дополнительным поиском на позицию, без engine search на каждого кандидата. Этот дополнительный поиск существует только в harness.

Старая модель: 8 реальных ответов на каждую позицию/Elo 600,800,1000,1200 — по 112 ответов/уровень. У неё нет seed API, поэтому сырые ответы сохранены; повторный сбор может дать другие числа. Это небольшой сравнительный baseline, не точная оценка её рейтинга.

Измеряются quality, utility loss, контрольная loss, частоты ходов, матов, guarded moves, задержки. Ни одному пользователю не отправляются analytics events.

## 7. Проверка монотонности

400 < 600 < 800 < 1000 < 1200 < 1400 < 1600 подтверждено **по средним потерям и качеству выбора на данном фиксированном наборе**. Это не доказательство результата head-to-head матчей или реального человеческого Elo.

Regression tests запускают по 14000 решений/уровень на трёх seeds. Loss и контрольная loss должны строго снижаться с запасом .001; допустимое отклонение долей best+good/mistake .3 процентного пункта, blunder .15 п.п. Отдельно проверяется снижение контрольной CP-loss на десяти позициях без матовых оценок. Результат не держится только на матах. Для 600 есть guard против best+good>=75% по production оценкам.

Unit/API проверки: нормализация CP/mate обоих цветов, границы quality, непрерывность, сумма вероятностей, RNG, modifiers, guardrails, повторяющиеся/неполные UCI строки, единственный ход, session restore, один engine search, реальные одинаковые позиции/seed дают одинаковые кандидаты и ход. Общая suite: 90 тестов проходят.

## 9. Производительность

Среднее нового поиска на 14 позициях: 254.0 мс; максимум 607.2 мс. Старый поиск в среднем 18.5 мс. Среда: Node v24.19.0 linux x64, тот же smallnet WASM. Новый анализ дороже, но остаётся менее секунды на этом наборе и этой машине.

- old: холодный первый ход с запуском WASM 258.4 мс; средний из пяти тёплых начальных ходов 22.3 мс.
- new: холодный первый ход с запуском WASM 551.3 мс; средний из пяти тёплых начальных ходов 319.4 мс.

Worker не блокирует UI поиском; проверка кандидатов в adapter на UI-thread добавляет небольшой разовый расчёт chess.js. На устройстве пользователя он пока отдельно не профилирован. Production использует один search; baseline/reference — инструменты проверки. При очень слабом устройстве возможен watchdog вместо хода; кнопка повтора использует существующий error flow.

## 10. Ограничения

- Нет калибровки на людях, нет матчевого рейтинга. Имена Elo здесь параметры внутренней модели; их нельзя переносить на FIDE/Chess.com.
- 14 позиций и повторные выборы — Monte Carlo по фиксированным условиям, не 98000 независимых шахматных ситуаций. Обобщение ограничено.
- Более глубокий reference использует тот же Stockfish и тоже не является абсолютной истиной. Например, у 1600 остаются ошибки по контрольным оценкам, хотя production классифицирует все выборы best/good.
- До 32 лучших ходов недостаточно для любой возможной позиции; fallback может сделать бота сильнее цели. При forced/equal positions это намеренно.
- Guardrail не полноценный SEE и не нейросетевая модель человека. Шаховые жертвы, долгие тактические sequences и античеловеческие тихие ошибки ещё возможны. В наблюдаемой серии 600 выбирал помеченную тихую отдачу тяжёлой фигуры примерно в 0.3% случаев; это не гарантия отсутствия всех видов зевков.
- Mate-in-2 зависит от того, нашёл ли Stockfish такой mate score в установленном бюджете. Распознавание модели не анализирует человеческую сложность рисунка мата.
- Для всей цепочки воспроизводимость проверена на одном WASM/Threads=1/бюджете. Между версиями движка fixtures и model version нужно обновлять. Watchdog не даёт случайный частичный ответ.
- Плавность проверена на сетке для средних и на каждом целочисленном Elo для базовых вероятностей, не для каждой возможной позиции. Точные доли ошибок не являются универсальными нормами человеческого Elo.
- Mobile Safari latency/нагрузка/батарея не измерены. Телеметрия не добавлена.

## 11. Рекомендации следующего этапа

1. Провести контролируемые тестовые матчи с игроками известного уровня или независимо калиброванными соперниками. Проверить комфорт и подогнать target offset, а не называть proxy настоящим Elo.
2. Добавить независимый holdout-набор и короткие engine tournaments с несколькими seeds/цветами. Отдельно оценивать партии и позиционный loss.
3. Замерить cold/warm latency, UI-thread preparation, память и расход батареи на iPhone/Android; при необходимости вынести подготовку контекста в worker и согласовать меньший фиксированный budget.
4. После этого рассматривать native-переход и более сильные уровни. Проверять стык отдельной симуляцией, не смешивать оба механизма weakening в одном поиске.
5. По конкретным примерам неестественных решений улучшать guardrail/phase и расширять позиции; не добавлять telemetry или personalities без отдельной задачи.

## Воспроизведение

```
npm run prepare:engine
npm test
npm run simulate:collect
npm run simulate
node scripts/simulation/performance.mjs
```

`simulate({fen,botElo,iterations,seed})` читает сохранённые candidates данной FEN; новую FEN сначала добавляют в `positions.mjs` и собирают реальным движком. `simulate({position,...})` принимает уже подготовленный fixture.
