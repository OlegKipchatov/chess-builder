# План миграции Chess Vault на React и TanStack Start

Статус: реализация React/Start в `preprod`. Экраны, хранилище и PWA перенесены; проверка и приёмка описаны в README. Выпуск в main и ручная проверка реального iPhone остаются отдельным этапом.
База: `main`, коммит `2a902f685db32d3259b839d497301698344233cf` — исправленная версия 10.

## Цель и границы

Разделить представление, правила игры, хранение и инфраструктуру, чтобы добавлять анализ партий, новые коллекции, достижения и аккаунты без роста общего DOM-контроллера. Перенести существующие возможности с сохранением поведения и данных. В рамках миграции не менять экономику, рейтинг, правила выпадения, алгоритм ослабления Stockfish и дизайн продукта.

React заменяет движок отображения; шахматным движком остаётся Stockfish 19, валидатором правил — chess.js. TanStack Start используется в SPA-режиме с TanStack Router. Серверные функции и SSR для игровой части на первом этапе не нужны. GitHub Pages не выполняет серверный код: подключение аккаунтов или серверных функций будет отдельным этапом с серверным хостингом.

## Стек и принципы

- React, TypeScript strict, TanStack Start/Router, Vite. Совместимые стабильные версии выбрать по peerDependencies при создании каркаса и зафиксировать точными версиями и lockfile; установка в CI через npm ci.
- CSS Modules для экранов и компонентов, общие CSS-токены и reset. Существующее оформление переносится без редизайна. SVG становятся React-компонентами.
- Vitest для сценариев состояния и компонентов, существующие node:test для правил и реального WASM сохранить до эквивалентного переноса. Playwright для проверки собранного приложения в Chromium и WebKit.
- TanStack Query добавлять при появлении удалённых данных; не использовать его как хранилище текущей партии. Redux/Zustand на старте не требуются.
- Стрелочные функции, именованные экспорты там, где их допускает API инструмента. Побочные эффекты не выполнять во время render или загрузки модуля.
- Не оборачивать старый app.js в React-компонент и не оставлять innerHTML-контроллер основой интерфейса. Временный адаптер допустим только с конкретным этапом удаления.

## Состояние и транзакции

Разделить три вида состояния:

1. Сохраняемое: коллекция, валюты, наборы, рейтинг, активная партия, история и флаги начисления.
2. Состояние сессии: актуальная позиция, запрос движка, результат, который ждёт закрытия диалога.
3. Представление: выбранная клетка, фильтры, открытый диалог, курсор архива, воспроизведение и анимация.

Сервис приложения предоставляет типизированные команды startGame, playMove, resign, openChest, craftItem, equipItem и saveSet, а также неизменяемый снимок через useSyncExternalStore. UI не записывает localStorage напрямую. Курсор и воспроизведение архива живут отдельно от активной партии. Не передавать изменяемый экземпляр Chess в React-состояние: наружу отдавать FEN, историю и вычисляемые данные.

Для каждой финансовой операции: вычислить следующий снимок → проверить допустимость → записать целиком → уведомить подписчиков → показать результат. При ошибке сохранения предыдущий снимок остаётся актуальным. Результат партии, награда, новый рейтинг и архивная запись фиксируются одной транзакцией. Повторный эффект или перезагрузка не должны начислять награды второй раз.

Жизненный цикл игры: idle → playing → resultPending → idle. Архив: отдельная replay-сессия. Завершение сохраняется сразу, но финальная доска видна до закрытия результата. После перезапуска сохранённый результат находится в истории без повторного начисления.

## Маршрутизация

- `/` — игра по умолчанию; `/collection`, `/chests`, `/craft`, `/profile`, `/faq`.
- `/profile/history/$gameId` — просмотр завершённой партии на общем компоненте доски; курсор изначально 0.
- При активной партии переходы через ссылки, адресную строку и Back/Forward возвращают пользователя на игру. Навигация и аватарка скрыты. Защита проверяется и в командах, а не только в UI.
- При загрузке сначала восстановить сохранение, затем разрешать переходы. Не показывать стартовый экран между загрузкой и восстановлением активной партии.
- Старые hash-ссылки преобразовать в новые маршруты. Не перехватывать неизвестные хеши как команды.
- Для статического размещения предрендерить фиксированные маршруты. Динамический маршрут архива требует SPA fallback или отдельного совместимого решения; проверить прямой вход и перезагрузку, а не только навигацию внутри приложения. На Pages нет обычных rewrite-правил: механизм fallback должен быть реализован и проверен явно.

## Доска, анимации и движок

- Стабильные ключи фигур и отдельный слой анимации: движение, взятие, рокировка, en passant, превращение, поворот доски и переходы в обе стороны по истории.
- Один контроллер переходов; быстрые повторные действия не создают параллельные несовместимые анимации. Учитывать prefers-reduced-motion.
- React управляет структурой; Web Animations API/ref допустимы для движения. Отмена анимаций и таймеров при смене сессии и размонтировании обязательна.
- Автопросмотр делает один полуход за шаг, ждёт завершения анимации, затем выдерживает интервал. Пауза, ручной переход, скрытие страницы и выход останавливают таймер. На последнем ходе воспроизведение прекращается; повторный старт начинает с нуля.
- Worker создаётся клиентским сервисом. Идентификатор сессии и запроса отбрасывает запоздавшие ответы после сдачи или смены партии. React StrictMode не должен запускать второго соперника.
- Сохранять профиль движка каждой начатой партии: новые используют Stockfish 19, ранее начатые завершаются на прежнем движке. Никакой тихой смены версии или силы при миграции.
- Не импортировать WASM, Worker, window или localStorage в выполняемую при предрендере логику. Проверить COOP/COEP, crossOriginIsolated, загрузку pthread и NNUE в реальном браузере, онлайн и офлайн.

## Данные и PWA

Формат chess-vault-v3 первоначально сохранить. Добавить типизацию и валидацию вокруг существующих миграций, не менять ключ только ради React. Фикстуры: v1/v2/v3, пустой профиль, повреждённый JSON, активная партия за обе стороны, архив и повторное открытие результата.

Перед будущим изменением схемы хранить резервный снимок и номер миграции; миграция должна быть повторяемой. Не удалять старые данные до успешной записи нового снимка. Preprod получает отдельный ключ, например chess-vault-preprod-v3, и собственную пустую коллекцию. Импорт production-снимка в preprod только отдельным действием пользователя; никакой автоматической записи обратно.

Service worker собирает precache из результата Vite, включая хешированные чанки, маршруты, CSS, SVG, Worker, WASM, NNUE и лицензии. Ручные суффиксы ?v=N удалить после завершения перехода. У каждой среды отдельные scope, manifest id/start_url и префикс кэша. Очистка касается только кэшей данной среды.

Обновление не применяется посреди партии. Сохранить прежнюю рабочую оболочку до успешного заполнения нового кэша. Проверить переход с версии 10 на React-версию, а не только чистую установку. Не удалять данные браузера для успешного прохождения теста обновления.

## Ветка preprod и тестовая публикация

Ветка `preprod` создаётся от исправленной main. На неё поступают отдельные законченные этапы; каждый сопровождается описанием того, что уже перенесено. Main не обновляется до завершения приёмки. Перед финальным PR подтянуть исправления main и повторить проверки.

Рекомендуемая тестовая публикация — отдельный origin на статическом хостинге с поддержкой rewrite и COOP/COEP. Конкретный адрес и подключение хостинга фиксируются на этапе 1; сейчас отдельный тестовый сайт не создан. Branch preview должен собираться из preprod после CI, показывать метку PREPROD и короткий SHA.

Если сохранять только GitHub Pages текущего репозитория, отдельная ветка не даёт второго сайта: публикация заменяет общий Pages artifact. Возможная альтернатива — единый artifact с production в корне и preprod в /preprod/. Но для него сначала нужны согласованный pipeline двух веток, сохранение обоих деревьев при каждом деплое и ограничение существующего production service worker областью production. При текущей логике очистки кэшей и перехвата запросов публиковать preprod вложенной папкой небезопасно для независимого тестирования. Не включать этот вариант молча.

До готовности отдельного адреса CI создаёт скачиваемый статический artifact и инструкцию локального запуска. Отсутствие внешнего preview не считать завершённой публикацией для тестирования.

## Этапы и критерии завершения

| Этап | Работа | Критерий перехода |
| --- | --- | --- |
| 0. Зафиксировать базу | Матрица возможностей, данные и текущие 70 тестов; эталонные мобильные/десктопные снимки исправленной версии | Воспроизводимый запуск, известны исходные сценарии |
| 1. Каркас и preprod | React/Start/TS, маршруты, CSS Modules, lockfile, CI, отдельный preview, изоляция данных | Чистая сборка, прямые URL работают; main и её PWA не изменились |
| 2. Домен и хранилище | Типизированные адаптеры, команды, миграции, useSyncExternalStore | Старые тесты и фикстуры проходят; ошибки записи не теряют прогресс |
| 3. Оболочка и коллекция | Навигация, профиль, FAQ, коллекции, наборы, сундуки, крафт | Все операции эквивалентны прежним, цены/шансы/компенсации неизменны |
| 4. Игра | Доска, выбор хода, случайная сторона, Stockfish, рейтинг, сдача и итоговый диалог | Полная партия за обе стороны, спецходы, восстановление и однократные награды |
| 5. Архив | Общая доска, переходы, анимации и старт/пауза | Просмотр с нуля, без изменения текущей партии; таймеры корректно отменяются |
| 6. PWA и обновление | Генерация precache, WASM/NNUE, изоляция и установка | Работа офлайн после установки; обновление версии 10 с сохранением прогресса |
| 7. Приёмка | Визуальная/функциональная проверка preprod, устранение регрессий | Пройдена матрица ниже, опубликована сборка с проверенным SHA |
| 8. Выпуск | PR preprod → main, production-конфигурация, проверка отката | Выпуск только после тестирования preprod; восстановление предыдущего artifact возможно |

Каждый этап — самостоятельный коммит/PR в preprod. Не совмещать миграцию с внедрением новых игровых функций. Это снижает число одновременно меняющихся условий и позволяет локализовать регрессии.

## Проверки, блокирующие выпуск

1. TypeScript, проверка CSS, линтер, тесты домена и сборка Start проходят на чистом checkout. Проверять собранный artifact, не только dev server.
2. Chromium и WebKit: ширины 375/390/430 и desktop; таблица стилей загружена, body имеет ожидаемую тему, доска 8×8, фигуры ограничены клетками, нет горизонтального переполнения. Снимки основных экранов и архива.
3. Сундук/крафт/повторы/сохранение набора, недостаток ресурсов, ошибка localStorage, повторная загрузка без удвоения операций.
4. Мат/пат/ничья/сдача, игра за чёрных, навигационные блокировки, ответ ИИ во время просмотра истории, перезагрузка во время хода ИИ.
5. Архив с нуля: шаги назад/вперёд/к последнему ходу, старт/пауза, окончание и повторный старт, смена страницы, скрытие вкладки. Никаких изменений PGN и наград.
6. Итоговая позиция остаётся за модальным окном до закрытия; после закрытия показано предложение сыграть, архив доступен в профиле.
7. Preprod не меняет production storage/caches/service worker. Проверить последовательное открытие обеих сред, а не только их независимый запуск.
8. PWA онлайн/офлайн, реальные Worker и WASM, обновление установленного приложения. Отдельная ручная проверка Safari/PWA на iPhone обязательна перед выпуском, браузерная эмуляция её не заменяет.
9. Доступность: кнопки с именами, клавиатура доски, фокус диалогов, возврат фокуса, контраст и reduced motion.

## Откат

До публикации сохранить предыдущий production artifact и SHA. Откат возвращает старую оболочку с новым номером кэша, чтобы она действительно обновила уже установленную PWA. Не удалять пользовательские сохранения. Если схема изменяется, заранее подтвердить совместимость старой версии или предоставить обратимую миграцию. Проверить откат на копиях данных до выпуска.

## Документация решений

- TanStack Start SPA mode: https://tanstack.com/start/latest/docs/framework/react/guide/spa-mode
- Static prerendering: https://tanstack.com/start/latest/docs/framework/react/guide/static-prerendering

SPA mode подходит для статического клиента, но требования к маршрутам и серверным возможностям необходимо решать отдельно. Наличие Start само по себе не добавляет сервер к GitHub Pages.
